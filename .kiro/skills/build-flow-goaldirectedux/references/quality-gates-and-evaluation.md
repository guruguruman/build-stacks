# Quality Gates and Evaluation Guide

このファイルは、GDD成果物の品質確認、検証、失敗パターン、評価指標を定義する。

---

## 1. 品質ゲート一覧

### Gate 0: Scope Gate

確認項目:
- 課題文がある。
- ビジョン文がある。
- 実行モードが明示されている。
- 非目標がある。
- 欠落情報がある。

失敗条件:
- 依頼文をそのまま機能実装タスクとして扱っている。
- 誰のどのゴールかが不明。

### Gate 1: Evidence Gate

確認項目:
- 証拠ログがある。
- `V/P/H` が付いている。
- 直近事例、行動、回避策、成功条件が含まれる。
- ステークホルダー、技術、制約情報がある。

失敗条件:
- 「ユーザーはたぶん」と推測だけで進めている。
- 機能要望だけを収集している。

### Gate 2: Persona Gate

確認項目:
- primary personaがある。
- primary選定理由がある。
- experience goalsとend goalsがある。
- 行動変数に基づいて分かれている。
- 証拠が紐づく。

失敗条件:
- 人口統計だけの人物カードになっている。
- 全員をprimary扱いしている。
- ペルソナが機能正当化の道具になっている。

### Gate 3: Scenario Gate

確認項目:
- context scenarioがある。
- key path scenarioがある。
- validation scenarioがある。
- 発端、文脈、制約、成功状態が書かれている。

失敗条件:
- クリック列だけになっている。
- 画面の中から始まっている。
- 成功条件がない。

### Gate 4: Requirements Gate

確認項目:
- 要件が「必要能力」として書かれている。
- UI部品名だけで要件化していない。
- 各要件がペルソナ、ゴール、シナリオに紐づく。
- 非目標がある。
- acceptance criteriaがある。

失敗条件:
- 要件が機能名の羅列。
- business/technical/legal constraintsが抜けている。

### Gate 5: Framework Gate

確認項目:
- 概念モデルがある。
- 情報設計がある。
- 主要フローがある。
- ナビゲーションがある。
- 必要ならサービスブループリントがある。

失敗条件:
- 画面単体のワイヤーだけで全体構造がない。
- primary personaの主導線が不明。

### Gate 6: Detailed Spec Gate

確認項目:
- empty/loading/success/error/partial-success/permission statesがある。
- エラー、再試行、取り消し、監査ログが扱われている。
- コピー、アクセシビリティ、計測がある。

失敗条件:
- 正常系だけ。
- 実装者が判断に迷う空白が多い。

### Gate 7: Build Handoff Gate

確認項目:
- 実装タスクが要件IDに紐づく。
- API/データ要件がある。
- テスト観点がある。
- acceptance criteriaがテスト可能。
- design decision logがある。

失敗条件:
- コードタスクがUX要件と切り離されている。
- 仕様変更の理由が残っていない。

### Gate 8: Validation Gate

確認項目:
- シナリオウォークスルーを行った。
- ユーザーテストまたは代替検証計画がある。
- 成功指標がある。
- 残留リスクがある。

失敗条件:
- 作って終わり。
- 仮説が検証されていない。

## 2. 典型的な失敗パターン

### 2.1 ペルソナポスター化

症状:
- 名前、年齢、趣味だけが詳しい。
- 要件や設計に使われていない。

修正:
- 行動変数、ゴール、証拠、シナリオを追加する。
- traceability matrixに紐づかない情報を削る。

### 2.2 機能防衛ペルソナ

症状:
- 作りたい機能を正当化するためにペルソナが作られている。

修正:
- その機能を支える証拠とシナリオを要求する。
- 証拠がなければ `H` として扱い、検証計画を付ける。

### 2.3 万人向け設計

症状:
- primary personaがない。
- すべての要望を1画面に入れる。

修正:
- primary/secondary/negativeを分ける。
- ゴールが衝突する場合は、接点やモードを分ける。

### 2.4 タスク列シナリオ

症状:
- 「クリックする」「入力する」だけで、文脈がない。

修正:
- 発端、利用環境、判断材料、失敗コスト、成功状態を追加する。

### 2.5 UI解の早すぎる固定

症状:
- 要件が「モーダルを出す」「ボタンを置く」になっている。

修正:
- 「ユーザーが何を知り、何を判断し、何を完了できる必要があるか」へ言い換える。

### 2.6 例外系の未設計

症状:
- 正常系だけで仕様が完成扱い。

修正:
- validation scenarioを最低5件作る。
- empty/loading/error/partial-success/permissionを全画面で確認する。

### 2.7 実装乖離

症状:
- 実装タスクがUX要件に紐づいていない。
- 開発中の制約で主導線が崩れる。

修正:
- design decision logを作る。
- 要件IDを実装チケットに付ける。
- 縮退案がprimary personaのend goalを壊さないか確認する。

## 3. 検証方法

### 3.1 シナリオウォークスルー

key path scenarioとvalidation scenarioを使い、設計を一歩ずつ検証する。

質問:
- この画面でペルソナは次に何をすればよいと分かるか。
- 判断に必要な情報は足りているか。
- 不安を解消するフィードバックがあるか。
- 失敗時に回復できるか。
- secondary personaの追加ニーズでprimary導線が壊れていないか。

### 3.2 ユーザーテスト

最小でも次を確認する。

- ユーザーが主要ゴールを達成できるか。
- どこで迷うか。
- どこで不安になるか。
- 何を確認しようとするか。
- エラー時に復旧できるか。
- 使われる語彙と画面ラベルが一致するか。

### 3.3 ログ検証

リリース後に見る指標:
- ゴール完了率。
- フロー離脱率。
- エラー率。
- 再試行率。
- 処理時間。
- サポート問い合わせ率。
- 差戻し率。
- 手戻り回数。
- 主要アクションの完了時間。
- ユーザー満足度、安心感、信頼感に関する調査。

## 4. 成功指標の作り方

成功指標は、ゴールに対応させる。

例:

| Goal | Metric | Example |
|---|---|---|
| 期限内に締め処理を終える | 完了時間 | 月次出力完了までの中央値 |
| 欠落を見逃さない | 除外理由確認率 | 出力前確認で除外理由を確認した割合 |
| 安心して実行する | 取り消し/再確認行動 | 不必要な再確認の減少 |
| 失敗から回復する | 再試行成功率 | 失敗後に自力復旧できた割合 |

---

## 5. 最終レビュー質問

最終提出前に自問する。

1. この設計は誰を最優先しているか。
2. その人のend goalは何か。
3. その人のexperience goalは何か。
4. 最も重要なcontext scenarioは何か。
5. 最も重要なvalidation scenarioは何か。
6. 要件はUI部品ではなく必要能力として書かれているか。
7. 実装者が迷う箇所は残っていないか。
8. 例外時にユーザーは回復できるか。
9. 何が仮説のままか。
10. 何を測れば成功と分かるか。
